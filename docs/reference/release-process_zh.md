# 发布流程

本参考文档记录了仅靠 CI 无法完全覆盖的发布准入条件。

## 标准发布准入条件

在发布版本之前，维护者需要验证：

- 版本号提升和包元数据已存在于发布分支中。
- 针对已修改代码的特定测试已通过。
- `bun run typecheck` 运行通过。
- 面向用户的文档已覆盖新的公开行为。
- 在最终确定发布日志之前，已知问题已记录在档。

CI 绿灯是发布准备就绪的必要条件，但对于复现步骤依赖于时序、服务商、模型或外部 OpenCode 行为的 Bug，CI 无法取代人工验证。

## 修复后的复现验证

在关闭原始 Issue 之前，竞态条件和并发问题的修复必须包含报告者验证过的复现确认。对于此类修复，CI 绿灯是必要的，但并不充分。

### 检查清单

- [ ] 原始 Issue 报告者（如果报告者不可用，则由维护者代替）针对修复提交重新运行已记录的复现步骤。
- [ ] 重新运行的结果记录在 Issue 讨论帖中，格式为 "Repro retested: PASS/FAIL on commit <SHA>"。
- [ ] 如果复现依赖于特定环境（特定的操作系统、模型、服务商），则在匹配的环境中尝试复现。
- [ ] 倘若无法进行复现，则在 Issue 关闭评论中明确说明，并在发布日志中记录为 "Fix unverified end-to-end"。

### 缘由

在历史上，通过了 CI 但从未针对原始复现步骤进行重新测试的竞态条件修复，在生产环境中经常出现回归。Issue #4006、#3996、#3962 是最近报告者确认较少的例子。针对 Issue #4012（促使 prompt-async-gate 产生的 Bug），报告者提供了详细的分析并推动了最终的修复，这种级别的修复后验证应该成为此类问题的标准规范。
