# 模型能力维护

本项目将模型能力解析视为一个分层系统：

1. 来自已连接服务商的运行时元数据
2. `models.dev` 捆绑或运行时的快照数据
3. 显式兼容性别名
4. 作为最后手段的启发式回退

## 内部策略

- 内置的 OmO 智能体或类别需求模型必须使用规范的模型 ID。
- 别名仅用于保持与历史 OmO 名称或服务商特定修饰的兼容性。
- 当规范的模型 ID 加上结构化设置可以表达相同内容时，不应将类似 `-high`、`-low` 或 `-thinking` 的新修饰名称添加到内置需求中。
- 如果服务商或配置输入仍在使用别名，请在边缘进行规范化，并在内部继续使用规范 ID。

## 添加别名时

- 将别名规则添加到 `src/shared/model-capability-aliases.ts` 中。
- 说明该别名存在的原因。
- 添加或更新测试，以便显式覆盖该别名。
- 确保别名的规范目标存在于捆绑的 `models.dev` 快照中。

## 防护栏

`bun run test:model-capabilities` 强制执行以下不变式：

- 别名的确切目标必须存在于捆绑的快照中
- 确切的别名键不能默默变成规范的 `models.dev` ID
- 模式别名不能重写规范的快照 ID
- 内置的需求模型必须保持规范且有快照支持

计划的 `refresh-model-capabilities` 工作流会在开启自动快照刷新 PR 之前运行这些防护栏。
